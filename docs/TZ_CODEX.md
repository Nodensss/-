## 0. Коротко (прочитай первым)

**Что есть сейчас.** Приложение на React 19 + Vite + TypeScript, сделано в Google AI Studio. Три вкладки: «321 → 323», «315 → 324», «Симуляция». Оператор вводит уровни и **сам считает расход за час**. Приложение показывает, сколько прибавится в расходной ёмкости после перекачки, на сколько хватит раствора и во сколько он закончится. Формулы и константы продублированы в `components/TankForm323321.tsx`, `components/TankForm315324.tsx` и `components/TankSimulation.tsx`.

**Чего хочет автор.** Чтобы этот расчёт работал прямо на мнемосхеме АСУ ТП: у ёмкости 321 стоит блок «Расчёт 321→323», у ёмкости 315 — блок «Расчёт 315→324». Уровни берутся из АСУ ТП. Расход считается автоматически: уровень расходной ёмкости час назад минус текущий.

**Твоя роль.** Доступа к АСУ ТП у тебя нет. Подготовь всё, чтобы служба АСУ ТП внедрила расчёт быстро и без ошибок, а у заявки были наглядные материалы:

1. **Этап 1.** Ядро расчёта `core/` и тесты. Формы и симуляция считают через ядро, результаты не меняются.
2. **Этап 2.** Авторасчёт расхода по истории уровня (окно 60 мин; перекачка не искажает расход). В формах — режим «расход по двум замерам» и улучшенный вывод.
3. **Этап 3.** Вкладка «Мнемосхема (макет)»: так блоки будут выглядеть в АСУ ТП. Сигналы имитируются.
4. **Этап 4.** Пакет для службы АСУ ТП `asutp/`: описание алгоритма, функциональный блок на ST (МЭК 61131-3), контрольные примеры, шаблон перечня сигналов, требования к экрану.
5. **Этап 5.** Материалы к заявке `umsh/`: пояснительная записка и скриншоты макета.

## 1. Предметная область

### 1.1 Схема

| | Связка 321 → 323 | Связка 315 → 324 |
|---|---|---|
| Ёмкость-источник (здесь готовят раствор) | 321, уровень в мм | 315, уровень в мм |
| Расходная ёмкость (из неё идёт дозирование) | 323, уровень в % | 324, уровень в мм |
| Неснижаемый остаток расходной `L_dead` | 30 % | 350 мм |
| Коэффициент `K`: сколько единиц расходной даёт 1 мм источника | 38 / 382 = 0,099476 %/мм (382 мм по 321 = 38 % по 323) | 1,2814 мм/мм (фактическая перекачка: 315 с 427 до 260 мм, 324 с 360 до 574 мм) |
| До какого уровня обычно откачивают источник `TARGET` | 160 мм или 0 | 260 мм или 0 |
| Типовые партии нового раствора `B`, мм по источнику | 382, 600, 900 | 300, 600, 900 |
| Максимальный уровень источника `L_src_max` | 634 мм | УТОЧНИТЬ (в симуляции шкала 800 мм) |
| Максимальный уровень расходной `L_feed_max` | УТОЧНИТЬ | УТОЧНИТЬ |
| Единица расхода `R` | %/ч | мм/ч |

Коэффициенты автор получил по фактическим перекачкам. Не меняй их, только перенеси в конфиг.

### 1.2 Текущие формулы (из кода)

```
X     = max(L_src − TARGET, 0)     сколько мм уйдёт из источника при перекачке
                                   (для 321 в коде ещё ограничение: не больше L_src_max = 634)
A     = X · K                      сколько прибавится в расходной
L_fin = L_feed + A                 уровень расходной после перекачки
U1    = max(L_fin − L_dead, 0)     полезный запас
H1    = U1 / R                     на сколько часов хватит
t1    = now + H1                   когда расходная дойдёт до L_dead
H_B   = B · K / R                  на сколько хватит новой партии B; закончится в t1 + H_B
```

`R` — расход из расходной ёмкости. Сейчас его вводит оператор вручную: %/ч для 323, мм/ч для 324.

### 1.3 Недостатки текущей версии (исправить на этапе 2)

- При `L_src ≤ TARGET` выводится только «перекачка не нужна». Не видно, на сколько хватит того, что уже есть в расходной.
- Время окончания показано без даты. При прогнозе больше суток непонятно, сегодня это или завтра.
- Часы десятичные («19.53 ч»), а оператору нужно «19 ч 31 мин».
- Нет проверки перелива расходной ёмкости при перекачке.
- Расход приходится считать в уме.

## 2. Термины

- **Источник** — ёмкость, где готовят раствор (321, 315). **Расходная** — ёмкость, из которой идёт дозирование (323, 324).
- **Расход `R`** — скорость убыли уровня расходной ёмкости, в её единицах за час.
- **Окно** — интервал, за который считается расход. По умолчанию 60 мин.
- **Отсчёт** — значение уровня, записанное раз в `DT` (по умолчанию раз в 1 мин).
- **Приток** — интервал, когда уровень расходной растёт из-за перекачки (или когда включён признак «идёт перекачка»).

## 3. Алгоритм

Алгоритм один для приложения, макета и АСУ ТП. Эталон — реализация в `core/` и контрольные примеры из Приложения Б. ST-блок (этап 4) должен давать те же результаты.

### 3.1 Входы (для каждой связки)

| Вход | Что это | Ед. |
|---|---|---|
| `L_src` | уровень источника (321 / 315) | мм |
| `L_feed` | уровень расходной (323 / 324) | % / мм |
| `ok_src`, `ok_feed` | достоверность сигналов | да/нет |
| `transfer_on` | признак «идёт перекачка» (насос или клапан). Есть ли такой сигнал в АСУ ТП — УТОЧНИТЬ. Если сигнала нет, всегда «нет» | да/нет |
| `TARGET` | до какого уровня откачивать источник (выбирает оператор) | мм |
| `B` | объём новой партии (выбирает оператор; 0 — не считать) | мм по источнику |
| `now` | текущее время | — |

### 3.2 Расход по истории (авторежим)

1. Раз в `DT` записываем отсчёт: `L_feed`, `ok_feed`, `transfer_on`. Храним последние `N + 1` отсчётов, где `N = WINDOW / DT` (по умолчанию 60).
2. Интервал `j` лежит между отсчётами `j−1` и `j`. Интервал **исключается**, если:
   - хотя бы один из двух его отсчётов недостоверен;
   - это **приток**: `transfer_on` включён в начале или в конце интервала, или `L[j] − L[j−1] > INFLOW_STEP`;
   - он стоит не дальше чем за `GUARD` интервалов **до** притока (захватываем начало перекачки);
   - он стоит не дальше чем через `SETTLE` интервалов **после** притока (ждём, пока уровень успокоится).
3. Неисключённые интервалы, идущие подряд, образуют **участок** — от отсчёта `a` до отсчёта `b`. Убыль на участке `ΔL = L[a] − L[b]`, длительность `(b − a) · DT`.
4. `T_ok` — сумма длительностей всех участков. Если `T_ok ≥ MIN_VALID`, то `R = ΣΔL / T_ok` (в час). Если перекачек и сбоев не было, это ровно «уровень час назад минус текущий».
5. Если `T_ok < MIN_VALID`, берём последний достоверный `R`, если с его расчёта прошло не больше `HOLD_MAX` (состояние «удержан»). Иначе состояние «нет данных». Сразу после запуска, пока истории меньше `MIN_VALID`, состояние «накопление».
6. Если `R < RATE_MIN` (в том числе отрицательный) — состояние «нет расхода», прогноз не строится.
7. Если текущий отсчёт `L_feed` недостоверен — состояние «недостоверно», прогноз не строится.

Порядок проверки: недостоверно → ручной режим → расход по окну → удержан → накопление → нет данных. Проверка `RATE_MIN` идёт после того, как `R` выбран.

Почему нельзя просто «было минус стало»: в примере Б5 за час была перекачка, и «было минус стало» даёт −35,5 %/ч. Расчёт по участкам без перекачки даёт верные 2,5 %/ч.

### 3.3 Расход по двум замерам (ручной режим в приложении)

```
R = (L_было − L_сейчас + X_пер · K) / Δt
```

`Δt` — часы между замерами (по умолчанию 1 ч). `X_пер` — сколько мм перекачали из источника между замерами (0, если не перекачивали). Если `R ≤ 0`, вывести «проверь замеры».

### 3.4 Прогноз

1. **Без перекачки:** `U0 = max(L_feed − L_dead, 0)`, `H0 = U0 / R`, `t0 = now + H0`.
2. **С перекачкой до `TARGET`:** формулы из раздела 1.2. Если `L_src ≤ TARGET` — «перекачка не нужна», `H1 = H0`.
3. **Перелив** (только если задан `L_feed_max`): если `L_fin > L_feed_max`, включить признак «перелив» и показать, до какого уровня можно откачать источник без перелива: `L_src − (L_feed_max − L_feed) / K`.
4. **Новая партия `B`:** `H_B = B · K / R`; партия закончится в `t1 + H_B`.
5. Если `L_src` недостоверен, пункты 2–4 не считаются, пункт 1 считается.
6. Признак «ниже неснижаемого остатка», если `L_feed < L_dead` (как сейчас).

### 3.5 Индикация (информационная)

| Статус | Условие |
|---|---|
| СРОЧНО | `L_feed ≤ L_dead` или `H0 < T_URGENT` |
| ВНИМАНИЕ | `H0 < T_WARN` |
| НОРМА | все остальные случаи, когда прогноз есть |
| НЕТ ПРОГНОЗА | накопление, нет расхода, нет данных, недостоверно (причину показать текстом) |

Дополнительные пометки: «идёт перекачка», «расход удержан (N мин назад)», «часть окна исключена (перекачка/сбой)», «РУЧН».

Цвет — подсказка оператору, а не технологическая сигнализация: без звука и без записи в журнал тревог.

### 3.6 Форматы

- Длительность: «19 ч 31 мин». Округление **вниз** до минуты с допуском 1e-6 мин. Без допуска в примере Б5 получится 18 ч 11 мин вместо 18 ч 12 мин.
- Время: «14:00». Если не сегодня — «завтра 03:31», если позже — «05.11 03:31».
- Время окончания считается от точных часов, округление только при выводе.
- В интерфейсе десятичная запятая, в CSV и тестах — точка.
- Расход: %/ч — 2 знака, мм/ч — 1 знак. Уровни: % — 1 знак, мм — целые.
- Время передаётся в расчёт параметром `now`. Внутри `core/` нет `new Date()`. Тесты создают дату через `new Date(год, месяц, день, ч, мин)` (локальное время) и не зависят от часового пояса машины.

### Этап 4. Пакет для службы АСУ ТП (`asutp/`)

- `ALGORITHM.md`:
  - назначение и ограничения;
  - входы, выходы и параметры (таблицы с единицами);
  - алгоритм по шагам (разделы 3.2–3.5) и коды состояний;
  - поведение при запуске, сбое датчика, перекачке, в ручном режиме;
  - как проверить свою реализацию на контрольных примерах;
  - где можно считать: в контроллере, на сервере АСУ ТП или в системе архивирования — алгоритм тот же; «значение час назад» можно брать и из архива.
- `FB_PEROX_PAIR.st` — функциональный блок на ST (МЭК 61131-3), по одному экземпляру на связку:
  - без расширений конкретных производителей, без ООП, указателей и динамической памяти;
  - кольцевой буфер `ARRAY[0..120]` (окно до 120 мин);
  - отсчёт берётся по переднему фронту входа `SAMPLE_TICK` (такт 1 мин формирует АСУ ТП); системное время внутри блока не используется;
  - выходы в часах; время суток считает экран: системное время плюс часы;
  - «не определено» — значение −1 плюс флаги достоверности;
  - защита от деления на ноль;
  - без `STRING` на выходах: состояния — кодами, тексты — на экране;
  - комментарии на русском;
  - таблица соответствия входов и выходов ST и `core/`.
  - Выходы: `RATE`, `RATE_STATE`, `USED_MIN`, `EXCL_MIN`, `TRANSFER_NOW`, `HOLD_AGE_MIN`, `BELOW_DEAD`, `H0`, `X_SRC`, `ADD_FEED`, `L_FIN`, `H1`, `H_BATCH`, `OVERFILL`, `SRC_MIN_NO_OVERFILL`, `STATUS`.
  - Коды `RATE_STATE`: 0 — по всему окну, 1 — часть окна исключена, 2 — удержан, 3 — накопление, 4 — нет расхода, 5 — нет данных, 6 — ручной, 7 — недостоверно.
  - Коды `STATUS`: 0 — НОРМА, 1 — ВНИМАНИЕ, 2 — СРОЧНО, 3 — НЕТ ПРОГНОЗА.
  - Те же коды использовать в `core/`.
- `test-vectors/` — контрольные примеры из Приложения Б в CSV: входные отсчёты и ожидаемые выходы. Тесты TypeScript читают эти же файлы.
- `HMI.md` — блоки на мнемосхеме: состав строк, форматы, цвета, что открывается по нажатию (параметры: цель перекачки, партия, ручной расход).

  - **Проблема.** Расход раствора из 323 и 324 и время до неснижаемого остатка на мнемосхеме не видны. Оператор считает вручную: замер, через час ещё замер, пересчёт мм в %, прогноз. Это занимает время (`[__]` мин за смену), в каждой смене считают по-своему, возможны ошибки. Если перекачку или приготовление сделать поздно, уровень может уйти ниже неснижаемого остатка — риск нарушить дозирование, а работы с перекисями приходится делать в спешке.
  - **Решение.** Два информационных блока на мнемосхеме у 321 и 315. Авторасход за 60 мин, время перекачки в расчёт не попадает. Прогноз без перекачки, с перекачкой и для новой партии. Индикация «Внимание» и «Срочно». Проверка перелива, если задан максимальный уровень. Делает служба АСУ ТП по процедуре управления изменениями, оборудование не нужно. Алгоритм отработан в калькуляторе автора, есть контрольные примеры и ST-блок.
  - **Эффект.** Надёжное дозирование. Работы с перекисями без спешки и с контролем перелива. Экономия времени оператора (`[__]`). Одинаковый расчёт для всех смен, без ошибок. Фактический расход виден сразу, отклонения заметны. Затраты — только работа АСУ ТП (`[__]` чел.-ч).
  - **Безопасность.** Расчёт информационный: не управляет оборудованием, не меняет сигнализацию, блокировки и ПАЗ.
- Скриншоты макета в `umsh/img/` (1280×800 и 390×844, масштаб 2) — если в окружении есть Playwright или Chromium. Специально их не ставить; если их нет, опиши в отчёте, как снять скриншоты вручную.

## 6. Ограничения

- **Безопасность процесса.** Расчёт — подсказка оператору. Он не управляет оборудованием, не формирует сигнализацию и блокировки, не меняет ПАЗ, не заменяет регламент и инструкции. Это написано в интерфейсе и в документации.
- **Информационная безопасность.** Приложение не подключается к АСУ ТП и не ставится на её станции. Никаких сетевых запросов, кроме CDN, которые уже есть в `index.html`.
- **Совместимость.** Не переносить и не переименовывать `index.html`, `index.tsx`, `App.tsx`, `vite.config.ts`. Importmap и CDN в `index.html` не трогать. `npm run dev` и `npm run build` работают.
- **Зависимости.** Новых runtime-зависимостей нет. devDependencies — только для тестов.
- **Код.** В `core/` и `sim/` нет `any`, `enum` и `namespace`. Единицы — в именах (`levelMm`, `ratePerHour`). Формулы — только в `core/`.
- **Язык.** Интерфейс, документация и комментарии — на русском, идентификаторы — на английском.
- **Не выдумывать.** Всё, чего нет в ТЗ и в коде, — параметр с пометкой `УТОЧНИТЬ` и значением по умолчанию из Приложения А.

## Возможное развитие (без отдельной задачи не делать)

- Уточнять `K` по фактическим перекачкам и показывать «K по факту» рядом с заданным.
- Пересчитывать расход в кг/ч перекиси, если известны плотность и концентрация раствора.
- Удельный расход на тонну продукта, если есть сигнал производительности.
- Метод наименьших квадратов вместо разности концов участков — меньше чувствительность к шуму.
- Строка «начать приготовление не позднее», если известна длительность приготовления.
